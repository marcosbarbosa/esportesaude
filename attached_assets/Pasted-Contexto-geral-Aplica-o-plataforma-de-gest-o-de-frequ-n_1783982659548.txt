Nos últimos dias, o sistema recebeu várias funcionalidades novas (frequência avançada, tablet grid, PA, atestados, anamnese, micro‑botões de WhatsApp, chamadas Gemini), e desde então os 502 ficaram mais frequentes.

Objetivo
>

Usar toda a capacidade técnica do agente para:

Detectar a causa real dos reboots da instância (saída do processo, OOM, exceções, health check falhando etc.).

Instrumentar logs internos de forma inteligente (apenas onde necessário) para ajudar a diagnosticar falhas futuras sem “gastar tokens demais” nem sobrecarregar o servidor.

Propor e implementar ajustes autocorretivos quando possível (time‑outs, try/except, circuit breakers, caching), mantendo o sistema estável.

Minimizar o custo: evitar soluções que gerem muito overhead ou logging excessivo.

>

Passo 1 – Análise precisa dos reboots e health checks
>

Inspecione os logs de aplicação imediatamente acima de cada linha ==> Running 'streamlit run main.py...'.

Procure por:

MemoryError, Killed, Out of memory ou qualquer mensagem de OOM.

Erros em módulos recentes (tablet, PA, atestado, anamnese, Gemini, WhatsApp).

Documente claramente qual padrão aparece mais antes dos reboots.

Passo 2 – Instrumentação de logs interna “cirúrgica”
>

Sem encher o código de prints, adicione logging estruturado apenas nos pontos críticos:

Entrada e saída das funções que:

Carregam grandes DataFrames de alunos (multi‑turmas, Freq.60D, atestados, PA, anamnese).

Fazem várias chamadas ao Supabase ou banco por request.

Chamam APIs externas (Google Gemini, WhatsApp, qualquer outro serviço externo).

Para cada ponto crítico, logue:

Tempo de execução (ms).

Tamanho de estruturas (nº de alunos, nº de registros).

Qualquer exceção capturada (stack trace resumido).

>

Use um nível de log adequado:

INFO para tempos e tamanhos.

WARNING para timeouts ou erros recuperáveis.

ERROR para exceções graves que derrubam o fluxo.

Evite logging de dados sensíveis (LGPD/saúde); basta IDs/tamanhos.

>

Garanta que o logging:

Seja centralizado (por exemplo, via módulo logging configurado uma vez em main.py).

Não faça I/O bloqueante excessivo (não escrever arquivos enormes; usar stdout que a Render já captura).

>

Passo 3 – Caça às causas prováveis de crash (McGyver mode)
>

Investigue, com base nos logs e no código:

Consultas pesadas (grandes DataFrame sem paginação ou sort_values sobre colunas sem índice).

Loops de recalculagem de frequência, PA, atestados, anamnese rodando a cada request.

Chamadas ao Gemini via google.generativeai:

Verifique se há timeouts, exceções não tratadas ou uso do SDK deprecado.

Passo 4 – Ajustes autocorrigíveis e de baixo custo
>

Proponha e implemente, no código:

Timeouts e retries para chamadas externas (Supabase, Gemini, WhatsApp), com circuit‑breaker simples:

Ex.: se um serviço falhar repetidamente, voltar temporariamente para um modo “offline” leve, sem tentar requisições pesadas.

Paginação ou limites de tamanho ao carregar listas de alunos:

Evitar carregar milhares de registros em cada mudança de filtro.

Cache leve de configurações estáveis (mensagens de WhatsApp, lista de turmas, textos estáticos).

>

Corrija o uso de componentes deprecados:

Localize todas as ocorrências de st.components.v1.html e substitua por:

from streamlit.components.v1 import html ou

st.iframe(url, ...), conforme o caso.
